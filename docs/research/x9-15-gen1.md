# ThinkPad X9-15 Gen 1 research

Machine types: `21Q6` and `21Q7`.

This document records physical/driver findings used by the ThinkControl X9 provider. It is research evidence for this exact device scope, not a general register map or authorization for other ThinkPads.

## Fan interface

Physical X9 testing established the classic ThinkPad EC control family:

```text
Fan control register   0x2F
Tachometer low byte    0x84
Tachometer high byte   0x85
Lenovo Auto            0x80
Manual states          1 to 7
```

Safety boundary:

```text
0x00 fan off            blocked
0x40 override family    blocked and unverified
continuous 0..100 PWM   no verified interface found
```

A specific `0x47` experiment is useful negative evidence: the control register echoed the value, but the physical fan remained at 0 RPM, while normal level 7 subsequently ramped to roughly 4400 RPM. ThinkControl therefore does **not** treat EC echo/readback alone as proof that the `0x40` family is a valid high-speed mode on this machine; the family remains blocked.

The working implementation uses PawnIO-backed I/O, bounded/tolerant EC reads, paced writes, duplicate-write suppression and standard ThinkPad EC mutexes. Modern Type-1 ports `0x1604/0x1600` are probed read-only before the older `0x66/0x62` fallback. A port pair is accepted only after a plausible ThinkPad fan-control state is read.

## Tachometer behavior and dual-fan investigation

The X9 tachometer sometimes failed to return both bytes reliably when `0x84` and `0x85` were accessed too aggressively. Repeated high-frequency RPM polling also correlated with periodic audible fan disturbance. ThinkControl therefore treats RPM as low-rate telemetry rather than a control-loop clock.

The X9-15 cooling assembly physically contains two fans. Released ThinkControl builds through alpha.35 deliberately used only the previously verified shared/system tachometer: they read `0x84/0x85` without selector writes and wrote `0x2F` once per requested EC state. That conservative model avoided an unverified register, but it also meant ThinkControl could not observe whether the two physical fans were actually synchronized.

On 2026-08-29, exact-device testing exposed a strong reason to revisit that assumption: a ThinkControl-managed state reported around 3500 RPM yet sounded substantially louder and produced a repeating wave/surge character, while Max Cooling around 4800 RPM sounded steadier and Lenovo's own Auto behavior was much smoother. This does not by itself prove the RPM reading was false. Two fans running at different speeds or repeatedly failing to settle can create strong acoustic beating even when one tachometer reports a plausible value.

Established dual-fan ThinkPad implementations such as TPFanCtrl2 use EC selector register `0x31` with selector values `0` and `1` around the shared `0x84/0x85` tachometer, and their dual-fan write path applies the requested `0x2F` state under both selectors before restoring the primary selector. This is strong comparative evidence, but it is still not a substitute for physical X9 verification.

The draft branch `fix/x9-dual-fan-control-stability` therefore treats `0x31` as an **exact-X9 test candidate only**:

```text
Fan selector            0x31
Primary selector        0x00
Auxiliary selector      0x01
Shared tachometer       0x84 / 0x85
```

The candidate implementation:

- reads both selected tachometers at low rate and exposes them separately as Fan 1 and Fan 2;
- applies each managed level `1..7` under both selectors with paced, bounded readback verification;
- applies `0x80` under both selectors when returning ownership to Lenovo Auto;
- restores selector `0` after each transaction;
- keeps duplicate-write suppression, so a stable requested level is not re-kicked every control-loop tick;
- remains gated to verified X9 machine types `21Q6`/`21Q7` and is not inherited by other Lenovo families;
- falls back toward Lenovo Auto after a failed managed write rather than continuously fighting firmware.

This branch must **not** be merged or released merely because hosted CI passes. Physical X9 validation is the blocking evidence. The required checks are: Lenovo Auto remains smooth with ThinkControl open; both RPM values are plausible; managed profiles ramp without the previous wave/beating behavior; returning to Auto settles both fans normally; and no unexpected zero-RPM or persistent fan-to-fan divergence appears.

## Read-only EC thermal fallback

Classic ThinkPad EC implementations expose thermal bytes at `0x78..0x7F` and `0xC0..0xC3`. ThinkControl may read plausible `5..125 °C` values from these banks on the already validated X9 transport when a richer provider does not expose a usable control temperature.

These registers remain deliberately unmapped in the public model:

- telemetry labels them as generic EC thermal entries rather than `CPU Package`;
- `CpuTemperatureC` is reserved for a provider that identifies CPU hardware;
- the fan supervisor may use the hottest valid X9 EC thermal value only as a conservative safety/control fallback.

This keeps supervised cooling recoverable during a sensor-provider gap without pretending an unknown EC byte has a known physical domain.

## Fan interfaces ruled out on the reference X9

Earlier diagnostics did not find a better continuous fan-control contract:

- no usable Legion-style WMI fan-control path;
- Intel IGCL exposed no chassis fan interface;
- standard ACPI `_FSL` control was absent;
- Lenovo `FANG` / `FANW` methods were absent;
- `IBMPmDrv` `GSFF/SSFF` did not provide the required backend.

These are findings for the tested X9 configuration, not claims that those interfaces are absent from all Lenovo laptops.

## Lenovo Intelligent Thermal Solution

Observed components included:

```text
Service       LITSSVC
ACPI device   ACPI\LEN0100
ACPI path     \_SB.PC00.LPCB.EC.ITSD
Version seen  2.2.111.0
```

This is a Lenovo thermal-policy layer, not direct PWM control.

### ThinkSmartSense / LITS IPC

Observed path:

```text
Commercial Vantage
  -> ThinkSmartSenseAddin
  -> \\.\pipe\com.lenovo.its.pipe.setting
  -> LITSSvc
```

IL inspection showed `IntelligentCoolingPipe.ChangeITSsetting(UInt32)` connecting to the pipe, writing one UInt32, flushing and reading one Int32 response. No JSON/complex framing was observed.

Reviewed command IDs:

```text
AC Eco           502
AC Balanced      503
AC Performance   504
DC Eco           507
DC Balanced      508
DC Performance   509
```

ThinkControl product UI exposes **Efficiency / Balanced / Performance**. The privileged service re-checks the exact X9 identity and AC/DC source before selecting an allowlisted command; the UI cannot submit a raw Lenovo command ID.

Lenovo has not published the meaning of the returned Int32. ThinkControl therefore treats receipt of the complete response as the observed protocol boundary and does not invent a `0 == success` rule.

This policy coordination follows the Windows power-preference change. It is intentionally separate from direct fan control.

## Windows Energy mode traces

A Process Monitor capture on battery while changing Windows Energy mode showed `LITSSvc.exe` updating `LITSSVC\IC\PSC\CurrentSetting`:

```text
Best power efficiency -> CurrentSetting 4
Balanced              -> CurrentSetting 6
Best performance      -> CurrentSetting 8
```

A broader trace also showed Intel Innovation Platform Framework activity. This supports keeping Windows power preference as the primary OS-level interface while treating LITS as an X9-specific OEM coordination layer.

## Lenovo Power Management

Observed on the X9:

```text
Service  IBMPMSVC
Device   \\.\IBMPmDrv
```

This interface is used only for functions with an established semantic/readback contract, such as keyboard backlight. No generic IOCTL guessing is permitted.

`LITSSvc.exe` also referenced `\\.\EnergyDrv`; ThinkControl similarly uses only recognized keyboard contracts and does not expose arbitrary driver calls.

## Current architecture model

```text
Windows power preference
    -> Windows / Intel platform policy
    -> Lenovo LITS may mirror/react

ThinkControl X9 Efficiency/Balanced/Performance
    -> Windows power preference
    -> semantic ThinkControl service request
    -> X9 identity gate + AC/DC detection
    -> allowlisted LITSSvc policy command

Direct X9 fan control (released baseline)
    -> verified PawnIO/device transport
    -> detected ThinkPad EC port pair
    -> verified fan register 0x2F
    -> states 1..7 or Lenovo Auto 0x80 with readback

Dual-fan candidate (draft; physical revalidation required)
    -> exact X9 identity gate
    -> selector 0x31 = 0 / 1
    -> shared tachometer 0x84/0x85 per selected fan
    -> paced 0x2F write/readback under both selectors
    -> selector restored to 0
    -> Lenovo Auto 0x80 on both selectors for handoff/failure recovery

X9 telemetry fallback
    -> low-rate EC tachometer reads
    -> generic read-only EC thermal banks when richer control temperature is absent
```

The Windows/OEM policy path and direct fan ownership remain separate capabilities.
