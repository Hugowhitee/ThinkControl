# ThinkPad X9-15 Gen 1 research

Machine types: `21Q6` and `21Q7`.

This document records physical/driver findings used by the ThinkControl X9 provider. It is research evidence for this exact device scope, not a general register map or authorization for other ThinkPads.

## Alpha.39 cooling conclusion

The alpha.38 experiments established two different Lenovo interfaces that must not be conflated:

1. **Other Mode fan attributes** can provide credible native per-fan RPM telemetry, but the tested `fanX_target` direct writer failed physical finished-product validation on the X9.
2. **LITSSvc / ThinkSmartSense thermal policy** is a reviewed semantic OEM policy path. Alpha.39 uses this path for the normal built-in Quiet/Balanced/Max cooling profiles so Lenovo firmware remains responsible for the actual closed-loop fan ramp.

The direct-writer rejection is physical evidence, not a metadata problem. Under a fixed alpha.38 target the real X9 repeatedly sped up/slowed down instead of settling smoothly, and nominal ThinkControl 100% remained below naturally hot Lenovo Auto. `FanSupervisor` was not continuously reissuing the manual target during that observation. Alpha.39 therefore keeps Other Mode target writes read-only, retains native telemetry plus target-0 Auto cleanup, and does not silently fall back to the known-inferior EC writer.

Current built-in cooling mapping on the verified X9 is:

```text
Quiet        -> Lenovo Quiet LITSSvc policy
Balanced     -> Lenovo Balanced LITSSvc policy
Max cooling  -> Lenovo Performance LITSSvc policy
Auto         -> clear cooling override and restore current power-policy baseline
```

This is firmware policy, not direct RPM/PWM control. Custom curves and manual percentages still require a future direct provider that independently passes physical acceptance.

## Fan interfaces

### Classic ThinkPad EC fallback

Physical X9 testing established the classic ThinkPad EC control family:

```text
Fan control register   0x2F
Tachometer low byte    0x84
Tachometer high byte   0x85
Lenovo Auto            0x80
Manual states          1 to 7
```

Safety boundary for the direct EC path:

```text
0x00 fan off            blocked
0x40 override family    blocked and unverified
continuous EC PWM       no verified interface found
```

A specific `0x47` experiment is useful negative evidence: the control register echoed the value, but the physical fan remained at 0 RPM, while normal level 7 subsequently ramped to roughly 4400 RPM. ThinkControl therefore does **not** treat EC echo/readback alone as proof that the `0x40` family is a valid high-speed mode on this machine; the family remains blocked.

Public `thinkpad-acpi` documentation gives an important semantic distinction that also matches the X9 observations: levels `0..7` are the normal firmware fan states, with level 7 the highest **recommended/normal** state; `auto` hands control to the EC's internal thermal algorithm; and the separate `full-speed`/`disengaged` family disables normal speed-locked control and may exceed the normal range. Therefore ThinkControl must describe X9 step 7 as the highest **verified standard EC state / fallback range**, not as proof of the laptop's absolute physical fan ceiling.

The EC implementation uses PawnIO-backed I/O, bounded/tolerant reads, paced writes, duplicate-write suppression and standard ThinkPad EC mutexes. Modern Type-1 ports `0x1604/0x1600` are probed read-only before the older `0x66/0x62` fallback. A port pair is accepted only after a plausible ThinkPad fan-control state is read.

Alpha.39 does not use this seven-step path as the normal X9 cooling backend. Once native Lenovo two-fan telemetry has been confirmed for the service lifetime, a transient native miss or rejected native writer does not silently re-authorize the EC writer. The EC code remains useful provider-specific research/diagnostic evidence for devices where that exact contract is actually validated.

### Lenovo Other Mode target-RPM evidence and rejection

PR #71 introduced a higher-capability candidate based on Lenovo's documented **Other Mode** WMI family and the behavior implemented by the upstream Linux `lenovo-wmi-other` driver. This is a different contract from classic EC levels; it exposes semantic fan RPM attributes instead of pretending a seven-step EC state is continuous control.

Relevant Lenovo WMI surfaces:

```text
LENOVO_OTHER_METHOD
GUID  DC2A8805-3A8C-41BA-A6F7-092E0089CD3B
GetFeatureValue         method 17
SetFeatureValue         method 18

LENOVO_CAPABILITY_DATA_00
GUID  362A3AFE-3D96-4665-8530-96DAD5BB300E
Per-attribute capability/default data

LENOVO_FAN_TEST_DATA
GUID  B642801B-3D21-45DE-90AE-6E86F164FB21
Per-fan reference minimum/maximum RPM data
```

The fan RPM attribute uses Lenovo device ID `0x04`, feature ID `0x03`, thermal mode `0`, and fan type IDs starting at `1`. Capability bits are `VALID`, `GET` and `SET`. The alpha.38 candidate required verified X9 identity, at least two independently live fan channels, write-capable metadata and sane Lenovo-reported RPM constraints before attempting a product write. Missing/inconsistent metadata remained read-only.

When that alpha.38 candidate passed its software gate:

- fan telemetry came from Lenovo `GetFeatureValue`;
- each fan got its own target calculated over its own Lenovo-reported min→max range;
- 0..100% curve/manual targets were continuous logical requests rather than seven-step EC aliases;
- the interface's documented target value `0` was reserved for **Auto handoff**, not the UI's 0% manual position;
- the UI's manual 0% meant the minimum reported running target, while 100% meant the maximum reported target for each fan;
- a failed partial multi-fan write triggered best-effort Auto cleanup for touched/owned channels;
- raw EC controls and seven-step calibration were hidden while this candidate was active;
- `FanSupervisor` remained the sole direct writer with thermal safety handoff and shutdown recovery.

Lenovo describes **Fan Test Data** min/max as reference/self-test values and notes a healthy firmware-controlled fan can run faster than the listed max or slower than the listed min. The upstream Lenovo driver still uses those values as its normal target-RPM constraints. The earlier research therefore explicitly required physical comparison against hot Lenovo Auto rather than assuming metadata maximum == physical maximum.

That physical acceptance test has now been run and **failed** on the reference X9:

- a fixed target repeatedly produced audible speed cycling/re-kick rather than stable settling;
- nominal 100% remained materially below naturally hot Lenovo Auto;
- the normal `FanSupervisor` loop was not repeatedly writing the fixed target, so the behavior cannot be dismissed as a simple 4-second rewrite bug.

Consequently alpha.39 sets the Other Mode direct-write authorization false. VALID+GET+SET, live readback and sane Fan Test values remain useful telemetry/provider evidence, but no longer authorize product target writes on this X9. The `fanX_input` read side stays active where credible. Target `0` remains available only for explicit cleanup/reassertion of firmware Auto after stale state from an earlier owned writer.

A future direct writer must start from fresh evidence. It must independently demonstrate two real fan channels, stable fixed-target settling without periodic re-kick, useful high-cooling range comparable with naturally hot Auto, and repeated clean Auto handoff. It must not be revived by simply extending Lenovo's reported target range or substituting an unrelated maintenance/high-speed command.

## Tachometer behavior and dual-fan investigation

The X9 EC tachometer sometimes failed to return both bytes reliably when `0x84` and `0x85` were accessed too aggressively. Repeated high-frequency RPM polling also correlated with periodic audible fan disturbance. ThinkControl therefore treats direct EC RPM as low-rate telemetry rather than a control-loop clock.

The X9-15 cooling assembly physically contains two fans. Released ThinkControl builds through alpha.35 deliberately used only the previously verified shared/system tachometer: they read `0x84/0x85` without selector writes and wrote `0x2F` once per requested EC state. That conservative model avoided an unverified register, but it also meant ThinkControl could not observe whether the two physical fans were actually synchronized.

On 2026-08-29, exact-device testing exposed a strong reason to revisit that assumption: a ThinkControl-managed state reported around 3500 RPM yet sounded substantially louder and produced a repeating wave/surge character, while Max Cooling around 4800 RPM sounded steadier and Lenovo's own Auto behavior was much smoother. A first exact-X9 dual-selector development build made the managed sound **somewhat better** and made a 100% manual request audibly stronger than before, but it still did not reproduce Lenovo Auto under high thermal load. This is evidence that the old single-channel/seven-step model was incomplete, but it is **not** evidence that step 7 should equal hot Lenovo Auto.

A second physical observation showed a separate telemetry problem: after changing to a quiet state, the UI could still display roughly 3800 RPM even though the fan had already become barely audible. The direct EC tachometer was intentionally polled only every 10 seconds and service status is cache-first, so an otherwise plausible previous reading could survive a fan-state change. The investigation branch invalidated the previous EC RPM immediately after a fan-state write/handoff, waited briefly for settling, and allowed a new managed-mode read at a bounded 6-second cadence. It did **not** turn tachometer access into a high-frequency servo loop.

### Selector `0x31`: telemetry evidence, not assumed independent control

Established ThinkPad code contains a secondary-fan selector at EC register `0x31`, bit/value `0/1`, around the shared `0x84/0x85` tachometer on selected dual-fan models:

```text
Fan selector            0x31
Primary selector        0x00
Auxiliary selector      0x01
Shared tachometer       0x84 / 0x85
```

Upstream ThinkPad evidence describes this primarily as a **tachometer selector**, while the main `0x2F` fan-control state affects both fans on known dual-fan implementations. Some third-party implementations perform extra selector choreography around control transactions, but that must not be generalized into a claim that the X9 has two independently addressable EC fan controls.

The X9 EC investigation used `0x31` only inside the exact-X9 fallback research. Ordinary Lenovo Auto discovery keeps the released shared-tach path and does not touch the selector merely because ThinkControl is open. While an explicitly active EC provider owns a managed state, it may read both selected tachometers at low rate so Fan 1/Fan 2 divergence can be observed rather than hidden behind one number. Native Lenovo Other Mode/EnergyDrv per-fan telemetry takes priority and this selector path is not the alpha.39 product cooling model.

## Read-only Lenovo Auto / OEM capture

`tools/research/Capture-LenovoAuto.ps1` is the evidence collector for cases where the documented target-RPM path is absent/rejected or still cannot match Lenovo Auto's useful high-cooling range. It is deliberately observational: it does not write EC registers, Lenovo registry values, power modes, services, ACPI methods or arbitrary IOCTLs.

During a capture it can record:

- ThinkControl `GetStatus`, including active provider, profile, control temperature, applied output and available fan channels;
- `LITSSVC\IC` state and LITSSvc service/version metadata;
- Windows power scheme and AC/DC state;
- read-only `EnergyDrv` `QueryFanSpeed` observations using `0x83102570` for fan indices 0/1;
- the known fan-state query `0x831020C4` with input `14`;
- hashes, relevant strings and known IOCTL constants found in locally installed Lenovo/driver binaries.

The script **never invokes** the public `EnergyDrv` `ChangeFanSpeed` IOCTL `0x8310257C`, the pulsing dust-removal/high-speed write `0x831020C0`, or guessed command values. Query values remain labelled raw until physical X9 correlation establishes their unit/meaning. An optional relevant-binary ZIP stays local until the user deliberately shares it.

The intended workflow is to capture naturally occurring states such as `lenovo-auto-hot`, `lenovo-auto-cool` and a managed comparison, then compare OEM/LITS/driver evidence. A future direct writer should be implemented only after an exact installed-X9 contract is recovered from evidence, never by brute-forcing `dwFanCtrlCmd` or nearby IOCTL values.

## Read-only EC thermal fallback

Classic ThinkPad EC implementations expose thermal bytes at `0x78..0x7F` and `0xC0..0xC3`. ThinkControl may read plausible `5..125 °C` values from these banks on the already validated X9 transport when a richer provider does not expose a usable control temperature.

These registers remain deliberately unmapped in the public model:

- telemetry labels them as generic EC thermal entries rather than `CPU Package`;
- `CpuTemperatureC` is reserved for a provider that identifies CPU hardware;
- the fan supervisor may use the hottest valid X9 EC thermal value only as a conservative safety/control fallback.

This keeps supervised direct cooling recoverable during a sensor-provider gap without pretending an unknown EC byte has a known physical domain.

## Other fan interfaces ruled out on the reference X9

Earlier diagnostics did not produce a usable smooth direct product-control path from these alternatives:

- no usable Legion-style fan-control path;
- Intel IGCL exposed no chassis fan interface;
- standard ACPI `_FSL` control was absent;
- Lenovo `FANG` / `FANW` methods were absent;
- `IBMPmDrv` `GSFF/SSFF` did not provide the required backend.

These are findings for the tested X9 configuration, not claims that those interfaces are absent from all Lenovo laptops. They also do not rule out future exact EnergyDrv/LITS direct-provider research; they simply are not substitutes for the rejected Other Mode writer in alpha.39.

## Lenovo Intelligent Thermal Solution

Observed components included:

```text
Service       LITSSVC
ACPI device   ACPI\LEN0100
ACPI path     \_SB.PC00.LPCB.EC.ITSD
Version seen  2.2.111.0
```

This is a Lenovo thermal-policy layer, not itself proof of direct fan-speed semantics.

### ThinkSmartSense / LITS IPC

Observed path:

```text
Commercial Vantage
  -> ThinkSmartSenseAddin
  -> \\.\pipe\com.lenovo.its.pipe.setting
  -> LITSSvc
```

IL inspection showed `IntelligentCoolingPipe.ChangeITSsetting(UInt32)` connecting to the pipe, writing one UInt32, flushing and reading one Int32 response. No JSON/complex framing was observed.

Reviewed command IDs:

```text
AC Eco           502
AC Balanced      503
AC Performance   504
DC Eco           507
DC Balanced      508
DC Performance   509
```

ThinkControl product UI exposes **Efficiency / Balanced / Performance** for Windows power preference. The privileged service re-checks exact X9 identity and AC/DC source before selecting an allowlisted command; the UI cannot submit a raw Lenovo command ID.

Lenovo has not published the meaning of the returned Int32. ThinkControl therefore treats receipt of the complete response as the observed protocol boundary and does not invent a `0 == success` rule.

Alpha.39 also reuses this reviewed semantic policy family for X9 **fan profile intent** without claiming direct fan speed. `LenovoCoolingPolicyCoordinator` stores the current Windows power-mode policy as a baseline, lets Quiet/Balanced/Max cooling temporarily select the corresponding Lenovo policy, and restores the newest baseline when Auto is selected. If the user changes Windows performance preference while a cooling profile is active, the baseline changes but the fan-profile override stays active. This resolves two product controls sharing one OEM policy surface without two loops repeatedly overwriting each other.

### What "Lenovo Auto" appears to mean

`0x80` on the classic ThinkPad EC path is a mode handoff: firmware owns the fan algorithm after that point. Lenovo's LITS layer additionally reacts to Windows/OEM power-policy state. Public LITSSvc binaries reference a family of `LITSSVC\IC` subkeys, and real systems have been observed updating `PSC\CurrentSetting` when Windows power mode changes. The exact numeric values vary by Lenovo generation/configuration, so ThinkControl must observe the X9 rather than copy another model's table.

The rejected Other Mode target-RPM path demonstrated why a semantic fixed target is not equivalent to every Lenovo Auto state: firmware can operate outside normal Fan Test target constraints and can apply its own smooth closed-loop behavior. Alpha.39 therefore uses Lenovo's policy layer for the built-in cooling intents and leaves future direct fan-control recovery as a separate research problem.

## Windows Energy mode traces

A Process Monitor capture on battery while changing Windows Energy mode showed `LITSSvc.exe` updating `LITSSVC\IC\PSC\CurrentSetting`:

```text
Best power efficiency -> CurrentSetting 4
Balanced              -> CurrentSetting 6
Best performance      -> CurrentSetting 8
```

Other Lenovo generations reported publicly use different values for comparable Windows modes. That reinforces that these numbers are observations for the tested X9/software stack, not a universal Lenovo command table.

A broader trace also showed Intel Innovation Platform Framework activity. This supports keeping Windows power preference as the primary OS-level interface while treating LITS as an X9-specific OEM coordination layer.

## Lenovo Power Management / EnergyDrv

Observed on the X9:

```text
Service  IBMPMSVC
Device   \\.\IBMPmDrv
```

`IBMPmDrv` is used only for functions with an established semantic/readback contract, such as keyboard backlight. No generic IOCTL guessing is permitted.

`LITSSvc.exe` also references `\\.\EnergyDrv`. Public reverse-engineering evidence distinguishes read/query contracts from fan writes, which is why the capture tool permits only the known read-side calls and static binary inspection. The dust-removal/high-speed command is explicitly unsuitable for smooth product fan control because that mode naturally pulses/cycles.

## Current architecture model

```text
Windows power preference
    -> Windows / Intel platform policy
    -> semantic ThinkControl SetThermalMode
    -> exact-X9 + AC/DC gate
    -> allowlisted LITSSvc policy command
    -> becomes the current restore baseline

X9 built-in cooling profile
    -> Auto / Quiet / Balanced / Max cooling
    -> LenovoCoolingPolicyCoordinator
    -> Quiet / Balanced / Performance semantic LITSSvc policy
    -> Lenovo firmware keeps actual closed-loop fan ownership
    -> Auto restores latest power-policy baseline

Lenovo Other Mode native fan telemetry
    -> LENOVO_OTHER_METHOD fanX_input attributes
    -> independently live per-fan RPM evidence
    -> preferred over classic shared EC tachometer where credible

Rejected Other Mode direct writer
    -> fanX_target metadata may expose VALID + GET + SET
    -> Fan Test Data supplies reference constraints
    -> alpha.38 physical fixed-target test failed smoothness/range acceptance
    -> product write authorization = false in alpha.39
    -> target 0 retained only for stale-owned Auto cleanup/reassertion

Classic EC direct path
    -> verified PawnIO/device transport
    -> standard EC states 1..7 only
    -> useful research/provider-specific fallback evidence
    -> not silently re-authorized after native OEM telemetry is established

EC dual-fan telemetry investigation
    -> exact X9 identity gate
    -> selector 0x31 = 0 / 1 only inside EC investigation
    -> shared tachometer 0x84/0x85 per selected fan
    -> selector restored to 0
    -> no claim of independently controllable EC fans

X9 telemetry/safety fallback
    -> bounded low-rate EC tachometer reads
    -> stale sample invalidated immediately after EC fan-state changes
    -> generic read-only EC thermal banks when richer control temperature is absent
```

`FanSupervisor` remains the sole owner of **direct fan writes**. `LenovoCoolingPolicyCoordinator` is separate and owns only the semantic firmware-policy override/baseline lifecycle. This split prevents the rejected direct writer from being revived merely to keep normal Quiet/Balanced/Max cooling usable.
