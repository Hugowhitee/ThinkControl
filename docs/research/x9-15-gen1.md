# ThinkPad X9-15 Gen 1 research

Machine types: `21Q6` and `21Q7`.

This document records physical/driver findings used by the ThinkControl X9 provider. It is research evidence for this exact device scope, not a general register map or authorization for other ThinkPads.

## Fan interface

Physical X9 testing established the classic ThinkPad EC control family:

```text
Fan control register   0x2F
Tachometer low byte    0x84
Tachometer high byte   0x85
Lenovo Auto            0x80
Manual states          1 to 7
```

Safety boundary:

```text
0x00 fan off            blocked
0x40 override family    blocked and unverified
continuous 0..100 PWM   no verified interface found
```

A specific `0x47` experiment is useful negative evidence: the control register echoed the value, but the physical fan remained at 0 RPM, while normal level 7 subsequently ramped to roughly 4400 RPM. ThinkControl therefore does **not** treat EC echo/readback alone as proof that the `0x40` family is a valid high-speed mode on this machine; the family remains blocked.

Public `thinkpad-acpi` documentation gives an important semantic distinction that also matches the X9 observations: levels `0..7` are the normal firmware fan states, with level 7 the highest **recommended/normal** state; `auto` hands control to the EC's internal thermal algorithm; and the separate `full-speed`/`disengaged` family disables normal speed-locked control and may exceed the normal range. Therefore ThinkControl must describe X9 step 7 as the highest **verified standard EC state / managed range**, not as proof of the laptop's absolute physical fan ceiling.

The working implementation uses PawnIO-backed I/O, bounded/tolerant EC reads, paced writes, duplicate-write suppression and standard ThinkPad EC mutexes. Modern Type-1 ports `0x1604/0x1600` are probed read-only before the older `0x66/0x62` fallback. A port pair is accepted only after a plausible ThinkPad fan-control state is read.

## Tachometer behavior and dual-fan investigation

The X9 tachometer sometimes failed to return both bytes reliably when `0x84` and `0x85` were accessed too aggressively. Repeated high-frequency RPM polling also correlated with periodic audible fan disturbance. ThinkControl therefore treats RPM as low-rate telemetry rather than a control-loop clock.

The X9-15 cooling assembly physically contains two fans. Released ThinkControl builds through alpha.35 deliberately used only the previously verified shared/system tachometer: they read `0x84/0x85` without selector writes and wrote `0x2F` once per requested EC state. That conservative model avoided an unverified register, but it also meant ThinkControl could not observe whether the two physical fans were actually synchronized.

On 2026-08-29, exact-device testing exposed a strong reason to revisit that assumption: a ThinkControl-managed state reported around 3500 RPM yet sounded substantially louder and produced a repeating wave/surge character, while Max Cooling around 4800 RPM sounded steadier and Lenovo's own Auto behavior was much smoother. A first exact-X9 dual-selector development build made the managed sound **somewhat better** and made a 100% manual request audibly stronger than before, but it still did not reproduce Lenovo Auto under high thermal load. This is evidence that the old single-channel model was incomplete, but it is **not** evidence that step 7 should equal hot Lenovo Auto.

A second physical observation showed a separate telemetry problem: after changing to a quiet state, the UI could still display roughly 3800 RPM even though the fan had already become barely audible. The cause was architectural, not a claim that the fan was physically still at that speed: the direct EC tachometer was intentionally polled only every 10 seconds and service status is cache-first, so an otherwise plausible previous reading could survive a fan-state change. The draft branch now invalidates the previous RPM immediately after a fan-state write/handoff, waits briefly for the fans to settle, and allows a new managed-mode reading at a bounded 6-second cadence. It does **not** increase RPM reads to control-loop frequency.

### Selector `0x31`: telemetry evidence, not assumed independent control

Established ThinkPad code contains a secondary-fan selector at EC register `0x31`, bit/value `0/1`, around the shared `0x84/0x85` tachometer on selected dual-fan models:

```text
Fan selector            0x31
Primary selector        0x00
Auxiliary selector      0x01
Shared tachometer       0x84 / 0x85
```

There is an important caution in upstream ThinkPad evidence: the selector is documented primarily as a **tachometer selector**, and the main `0x2F` fan-control state is described as affecting both fans on the known dual-fan implementations. Some third-party implementations perform extra selector choreography around control transactions, but that must not be generalized into a claim that the X9 has two independently addressable fan controls. The X9 still needs physical evidence for the exact selector semantics.

The current draft therefore uses `0x31` only within the exact-X9 investigation boundary. Ordinary Lenovo Auto status discovery keeps the released shared-tach path and does not touch the selector merely because ThinkControl is open. While ThinkControl owns a managed state, the candidate can read both selected tachometers at low rate so Fan 1/Fan 2 divergence can be observed rather than hidden behind one number. The PR remains blocked from release until the selector behavior and control transaction are physically revalidated.

Required physical checks remain: Lenovo Auto stays smooth with ThinkControl open; selected Fan 1/Fan 2 readings are plausible; managed profiles ramp without the old wave/beating behavior; returning to Auto settles normally; and no unexpected zero-RPM or persistent fan-to-fan divergence appears.

## Read-only Lenovo Auto capture

`tools/research/Capture-LenovoAuto.ps1` is an evidence collector for this investigation. It is deliberately read-only: it does not write EC registers, Lenovo registry values, power modes, services, ACPI methods, IOCTLs or firmware. During a capture it records:

- the current ThinkControl `GetStatus` snapshot, including profile, control temperature and available fan channels;
- the current `LITSSVC\IC` registry subkeys/values;
- LITSSVC service/version metadata;
- the active Windows power scheme and AC/DC state.

The intended workflow is to capture naturally occurring states such as `lenovo-auto-hot`, `lenovo-auto-cool` and a separate managed step-7 comparison, then diff the observations. This is safer and more useful than guessing undocumented registry values or EC bytes.

## Read-only EC thermal fallback

Classic ThinkPad EC implementations expose thermal bytes at `0x78..0x7F` and `0xC0..0xC3`. ThinkControl may read plausible `5..125 °C` values from these banks on the already validated X9 transport when a richer provider does not expose a usable control temperature.

These registers remain deliberately unmapped in the public model:

- telemetry labels them as generic EC thermal entries rather than `CPU Package`;
- `CpuTemperatureC` is reserved for a provider that identifies CPU hardware;
- the fan supervisor may use the hottest valid X9 EC thermal value only as a conservative safety/control fallback.

This keeps supervised cooling recoverable during a sensor-provider gap without pretending an unknown EC byte has a known physical domain.

## Fan interfaces ruled out on the reference X9

Earlier diagnostics did not find a better continuous fan-control contract:

- no usable Legion-style WMI fan-control path;
- Intel IGCL exposed no chassis fan interface;
- standard ACPI `_FSL` control was absent;
- Lenovo `FANG` / `FANW` methods were absent;
- `IBMPmDrv` `GSFF/SSFF` did not provide the required backend.

These are findings for the tested X9 configuration, not claims that those interfaces are absent from all Lenovo laptops.

## Lenovo Intelligent Thermal Solution

Observed components included:

```text
Service       LITSSVC
ACPI device   ACPI\LEN0100
ACPI path     \_SB.PC00.LPCB.EC.ITSD
Version seen  2.2.111.0
```

This is a Lenovo thermal-policy layer, not direct PWM control.

### ThinkSmartSense / LITS IPC

Observed path:

```text
Commercial Vantage
  -> ThinkSmartSenseAddin
  -> \\.\pipe\com.lenovo.its.pipe.setting
  -> LITSSvc
```

IL inspection showed `IntelligentCoolingPipe.ChangeITSsetting(UInt32)` connecting to the pipe, writing one UInt32, flushing and reading one Int32 response. No JSON/complex framing was observed.

Reviewed command IDs:

```text
AC Eco           502
AC Balanced      503
AC Performance   504
DC Eco           507
DC Balanced      508
DC Performance   509
```

ThinkControl product UI exposes **Efficiency / Balanced / Performance**. The privileged service re-checks the exact X9 identity and AC/DC source before selecting an allowlisted command; the UI cannot submit a raw Lenovo command ID.

Lenovo has not published the meaning of the returned Int32. ThinkControl therefore treats receipt of the complete response as the observed protocol boundary and does not invent a `0 == success` rule.

This policy coordination follows the Windows power-preference change. It is intentionally separate from direct fan control.

### What "Lenovo Auto" appears to mean

Current evidence does not point to one hidden RPM "secret key". `0x80` is a mode handoff: the embedded controller/firmware owns the fan algorithm after that point. Lenovo's LITS layer additionally reacts to Windows/OEM power-policy state. Public LITSSvc binaries reference a family of `LITSSVC\IC` subkeys, and real systems have been observed updating `PSC\CurrentSetting` when Windows power mode changes. The exact numeric values vary by Lenovo generation/configuration, so ThinkControl must observe the X9 rather than copy another model's table.

That makes the useful reverse-engineering target the **inputs/state transitions around Auto**, not an invented direct fan byte: compare LITS registry state, Windows power state, EC mode, temperatures and real fan response while Lenovo controls cooling.

## Windows Energy mode traces

A Process Monitor capture on battery while changing Windows Energy mode showed `LITSSvc.exe` updating `LITSSVC\IC\PSC\CurrentSetting`:

```text
Best power efficiency -> CurrentSetting 4
Balanced              -> CurrentSetting 6
Best performance      -> CurrentSetting 8
```

Other Lenovo generations reported publicly use different values for comparable Windows modes. That reinforces that these numbers are observations for the tested X9/software stack, not a universal Lenovo command table.

A broader trace also showed Intel Innovation Platform Framework activity. This supports keeping Windows power preference as the primary OS-level interface while treating LITS as an X9-specific OEM coordination layer.

## Lenovo Power Management

Observed on the X9:

```text
Service  IBMPMSVC
Device   \\.\IBMPmDrv
```

This interface is used only for functions with an established semantic/readback contract, such as keyboard backlight. No generic IOCTL guessing is permitted.

`LITSSvc.exe` also referenced `\\.\EnergyDrv`; ThinkControl similarly uses only recognized keyboard contracts and does not expose arbitrary driver calls.

## Current architecture model

```text
Windows power preference
    -> Windows / Intel platform policy
    -> Lenovo LITS may mirror/react

ThinkControl X9 Efficiency/Balanced/Performance
    -> Windows power preference
    -> semantic ThinkControl service request
    -> X9 identity gate + AC/DC detection
    -> allowlisted LITSSvc policy command

Lenovo Auto cooling
    -> EC 0x2F = 0x80 ownership handoff
    -> internal firmware thermal algorithm
    -> Lenovo/Windows thermal-policy inputs may influence platform behavior
    -> not equivalent to manual EC step 7

Direct X9 managed fan control
    -> verified PawnIO/device transport
    -> detected ThinkPad EC port pair
    -> standard EC states 1..7 only
    -> duplicate-write suppression + readback

Dual-fan telemetry candidate (draft; physical revalidation required)
    -> exact X9 identity gate
    -> selector 0x31 = 0 / 1 only inside managed investigation
    -> shared tachometer 0x84/0x85 per selected fan
    -> selector restored to 0
    -> no claim of independently controllable fans

X9 telemetry fallback
    -> bounded low-rate EC tachometer reads
    -> stale sample invalidated immediately after fan-state changes
    -> generic read-only EC thermal banks when richer control temperature is absent
```

The Windows/OEM policy path and direct fan ownership remain separate capabilities.
