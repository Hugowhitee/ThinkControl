# X9 local control-path recovery, 2026-10-05

Scope: reference X9-15 21Q6, BIOS N4CET45W 1.21, LITS 2.2.111.0. This note supersedes the earlier full-speed direct-ID fallback for this machine. Historical experiments remain evidence, not current authorization.

## Unsupported getter mistaken for full speed

Read-only extraction obtained the current 300544-byte DSDT, SHA-256 `D95DF65306DD24894BC69295075E11CF5278C3EEA2EAE5F0A8BFBA7F3E4B0738`, plus 28 Windows-published SSDT registry copies. ACPICA iASL 20260408 disassembled these offline; no ACPI method was evaluated and no EC write occurred. The official tool release-asset digest was checked before execution. Raw tables and Lenovo binaries remain private ignored evidence. Windows GetSystemFirmwareTable retrieves only the first duplicate signature; registry copies supplied the other published SSDTs.

The DSDT `_SB.GZFD._WDG` maps GUID `DC2A8805-3A8C-41BA-A6F7-092E0089CD3B` to `WMLA`, object ID `LA`. This is the live LENOVO_OTHER_METHOD class GUID. Its method-17/GetFeatureValue branch handles `0x08010001`; it has no full-speed `0x04020000` or per-fan RPM branch. Unhandled requests fall through to `Return (One)`. The live schema contains no SetFeatureValue method.

The earlier full-speed GET value **1 is the unsupported fallback**, not proof that either fan runs at full speed or that another utility owns cooling. Candidate detection now requires this exact feature's advertised VALID+GET capability before interpreting a value, plus SET and the live setter before writes. Missing capability fails closed without painting the fallback as fan state.

The installed alpha.60 Return-to-Auto request failed with ManagementException while pursuing the nonexistent setter. Candidate capability/error/UI handling addresses this detection failure; it does not establish a stable direct writer or prove an installed candidate's Auto handoff.

## Distinct interfaces and open hypotheses

- DYTC dispatch and capability checks are present. This remains a thermal/platform-policy lead. Recover the exact installed Windows transport, capability, source, ownership and restoration contract before using a new writer.
- HKEY PWMC returns zero; PWMG reads two EC fields. No accompanying setter is defined. Names and field presence do not establish direct fan-duty control; their physical meaning remains uncorrelated.
- FAN0 SRPM assigns software CRPM; `_FST` reports that value only for selected PSC states. This code does not drive a fan controller.
- The DSDT/registered SSDT analysis found no definitions of FANG/FANW, standard `_FSL`, or GSFF/SSFF. IBMPmDrv contains GSFF/SSFF names; binary presence is not firmware implementation evidence.
- [Upstream thinkpad_acpi](https://github.com/torvalds/linux/blob/master/drivers/platform/x86/lenovo/thinkpad_acpi.c) maps its classic backend's pwm facade to discrete EC levels. The name does not establish continuous PWM; Auto, regulated levels and disengaged full speed differ.
- [TPFanCtrl2](https://github.com/mews-se/TPFanCtrl2/blob/main/fancontrol/fanstuff.cpp) uses changed-state checks and EC level commands with fan selectors. Its tested devices do not establish X9 selector/control semantics.

Earlier alpha.38 fixed RPM targets already produced audible cycling without periodic supervisor rewrites. Rewrite frequency alone is insufficient. OEM/firmware contention, control-mode prerequisites, channel mapping and telemetry correlation remain open. Rejected targets and EC steps must not be re-enabled without a new verified contract.

## One-command observation

Hypothesis: a single already-allowlisted AC Performance request changes OEM PSC state without repeated writes. Through the installed service, one SetThermalMode Performance request sent existing command 504; a 40-second observation took nine samples. The service reported transport acceptance without an Int32 reply. PSC stayed **2**; shared EC RPM varied **3644–4056**, CPU temperature **51–70°C**. This does not establish a causal fan response. Acoustic observation was not obtained: the user asked whether the test had begun after it ended. Announce future listening tests clearly before the command.

Gen-8 PSC=2 is energy saver in the installed ThinkSmartSense reader. The existing Quiet restoration request was sent; PSC=2 and Auto profile were read back. Alpha.60 IPC does not expose its in-memory thermal baseline; PSC restoration does not separately prove that private state. Subsequent static tracing found that this pipe route can call SetWindowsPowerMode. Both source preferences were therefore checked and explicitly restored: AC Performance and DC Efficiency already matched the original baseline before restoration; native restoration returned zero and the High performance plan was verified. Battery limits, service states and custom direct targets were not changed.

Next useful lead: recover the exact DYTC/PSC Windows bridge and active-policy readback. Repeating 504 because IPC says success adds no evidence. Cool/LCM/Improved Cooling Efficiency remain research-only: the required capability keys are absent. LenovoProcessManagement dispatcher is absent, so the adaptive add-in's service commands are not applicable here.

## Verified Windows DYTC transport

Static inspection of the installed LITSSvc 2.2.111.0 (no OEM execution) recovered these exact call sites:

- RVA `1E2C0` opens `\\.\IBMPmDrv` with GENERIC_READ, FILE_SHARE_READ and OPEN_EXISTING. DeviceIoControl uses a four-byte command and four-byte reply. RVA `1E410` uses IOCTL `0x22270C`, packing function in bits 12–15, mode in 16–19 and enable in bit 20, with SET command 1. The local DSDT DCSE independently confirms this layout.
- RVA `4AD90` maps Gen<9 AC Performance to PSC function 13, mode 7, enabled. It invokes the preceding setter, then updates the registry mirror only on accepted execution. Energy saver is mode 2. These are platform policy modes, not fan percentages or target RPM.
- Pipe command 504 first enters a Windows source-preference setter. Its acknowledgment cannot substitute for firmware state; fan and performance settings through that route can overlap.

A bounded, fixed-query local reader invoked only DYTC QUERY=0, GET=2 and function capabilities=3. All returned exactly four bytes with native success: `0x80000101` (query), `0x20012D01` (function 13, mode 2), and `0x79910001` (function mask `0x7991`, PSC supported). This proves the real read path is accessible on this machine without installing another driver. It does not prove a fan writer. Registry PSC is a mirror, not the authoritative GET.

The physical probe is limited to the exact firmware/identity and captured mode-2 baseline: one `0x0017D001` Performance command, read-only observations, and `0x0012D001` restoration in finally. No generic IOCTL interface, arbitrary setter, EC write or automatic loop enters the product from this research harness. Physical and acoustic results must be recorded separately before selecting a provider.

Result: Performance read back as function 13/mode 7 for all 19 samples over 90 seconds without another setter. CPU was 56–69°C; shared tachometer remained 4800 RPM. The user reported **no audible difference from before**. Baseline function 13/mode 2 was restored, verified immediately and after five seconds, then independently queried again. Registry PSC remained 2 throughout the actual mode-7 interval: it demonstrably lagged authoritative firmware state. This proves stable policy selection and restoration, not a physical fan response.

A subsequent elevated read-only EC check used the existing mutex-protected transport and no selector/control writes. It read HFSP `0x80` (firmware Auto, no full-speed bit), 4800 RPM. Thus this observation was not a leftover EC full-speed override. The ordinary-user EC attempt correctly failed with access denied; the DYTC reader was independently accessible. The elevation was for observation only and its process exited.

## Exact EC full-speed state: physical progress, readback remains open

The local DSDT MHAT treats **HFSP exactly `0x40`** as a preserved full-speed condition. Other values go through its regulated/Auto assignment. The classic product constant `0x47` combines the standard full-speed bit with level 7; that is not the same exact firmware comparison. This new device evidence justified a single-state experiment; it does not establish continuous PWM or revive the seven-level writer.

An exact-21Q6/N4CET45W probe sent `0x40` once with no selector changes. Over 90 seconds, control samples stayed `0x40`; service tachometer rose from 4800 to roughly 9400–9656 RPM and direct reads corroborated high speed. CPU fell to 49°C at the last observation. The user said it felt like 100%, clearly did something, and sounded consistent. They specifically require that sub-maximum control not be presented as 99% if it only produces much lower cooling.

The first 100-ms Auto verification failed (still read `0x40`). Existing best-effort/disposal cleanup subsequently returned the controller to `0x80`; an independent elevated reader confirmed Auto and 3800 RPM. The original failure remains in the experiment record. This does not yet distinguish settling latency, retries or stale register reads.

A second bounded probe tested waiting up to one second after each single write. Auto readback succeeded immediately and after ten seconds, and RPM declined. However, its baseline read reported `0x04` just after its initial guard read `0x80`, with no setter between them; another `0x04` appeared at the end while direct RPM was still 9400. The probe stopped rather than reissued full speed. Whether firmware reclaimed control or EC transactions returned stale data remains unresolved. The whole-solution build ran during this second probe, so its CPU changes are not an isolated thermal comparison.

The existing WaitForReadReady waits for OBF for only five milliseconds, then treats IBF-clear as returned data. [ACPI's embedded-controller protocol](https://uefi.org/specs/ACPI/6.5/12_Embedded_Controller_Interface_Specification.html) distinguishes input accepted (IBF-clear) from output ready (OBF-set). A strict OBF-only read harness is the next hypothesis test; it calls no setters or selectors. Do not promote Max or advertise arbitrary percentages until state/rollback verification is reliable.

Strict OBF-only result: neither port pair validated; the legacy read timed out. This experiment does not justify replacing the fallback with a permanently unavailable provider. [LibreHardwareMonitor's reader](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/master/LibreHardwareMonitorLib/Hardware/Motherboard/Lpc/EC/WindowsEmbeddedControllerIO.cs) identifies its IBF fallback as an ASUS workaround. The X9's DSDT places HFSP in the SystemMemory ECOR region (`0xFE0B0A00`) and also declares a legacy EmbeddedControl region/ports. H8DR selects mapped fields on modern Windows; global RBEC/WBEC use the firmware SMI helper. This is a distinct path worth investigating, not authorization for raw memory/SMI writes.

The bundled [PawnIO LpcACPIEC source](https://github.com/namazso/PawnIO.Modules/blob/main/LpcACPIEC.p) permits only 0x62/0x66. A rejected attempt at 0x1600/0x1604 through that module cannot prove the hardware lacks those ports. The upstream ThinkPad request remains open; do not bypass the module allowlist or install an unrestricted driver. Current DSDT legacy resource declarations are 0x62/0x66.

User follow-up: the second probe also sounded loud and effective. The installed app usually shows one fan measurement and occasionally two, although the assembly has two fans. Stable source/channel identity and true second-channel measurement remain required; duplicating the shared tachometer is prohibited.

Further bounded verification: a 15-ms IBF fallback retained `0x40` throughout a third 30-second probe, but a single Auto request still failed readback; existing cleanup subsequently restored `0x80`, independently verified. A fourth probe used one full-speed write and allowed the normal three bounded Auto attempts. At 15 seconds it reported `0x04` while service RPM was 9500 and aborted without rewriting full speed. Its write log contains exactly `0x40`, `0x80`. The restoration flag was true, but the adjacent post-IPC samples reported `0x04`; that flag alone is insufficient evidence. A separate read-only observer then obtained fourteen consecutive `0x80` readings over 32 seconds, RPM 4612–4800. The physical full-speed response is established; reliable state observation under service activity remains open.

Local source improvements keep LHM channel IDs derived from the provider's sensor ID, sorted consistently, instead of assigning identity from enumeration order. They do not fabricate a second channel or retain expired RPM as live. The X9 profile's old claim of accepted levels 1–7 is removed; the production writer remains disabled. The existing dual-selector candidate also needs review: writing all of register `0x31` would clear other firmware fields (HUWB, VPON, VRST); bit preservation and restoration must precede any dual-channel acceptance test.

Read-only status correlation obtained transient `0x04` around three of five IPC calls; all five samples after an additional 1100-ms pause read `0x80`. A follow-up full-speed probe added that pause. It retained `0x40` at each active observation, direct RPM reached 9500, and immediate/ten-second Auto samples both read `0x80`, direct RPM declining to 5400. Exactly one `0x40` and one `0x80` were written. Its baseline still reported `0x04` after the initial Auto guard; the pause improves this observation but is not a universal reader correction or product acceptance.

The dual-selector candidate now read-modify-writes bit zero, verifies selection, and restores the original channel with current unrelated bits retained; exhaustive tests cover every starting byte and both selectors. This candidate remains inactive in passive/Auto telemetry. Product IPC also explicitly marks a shared tachometer, so the UI calls it a shared reading rather than implying one physical fan. The Other Mode provider's unadvertised direct-ID fallback is now opt-in research only: unsupported getter value 1 cannot authorize production fan telemetry merely because Fan Test metadata contains a range.

## Adaptive thermal ownership lead

The installed IBM driver routes IOCTL `0x2224A8` to HKEY.MHQT, `0x2224AC` to MHGT and `0x2224B0` to MHAT, through its inspected four-byte ACPI argument/reply adapter. The current DSDT defines these methods and rejects absent WNTF/TATC with zero. Read-only queries returned MHQT(0)=1, MHQT(1)=`0x00330011`, MHQT(2)=`0x11`, MHQT(4)=1, and MHGT(0)=`0x09002828`. This establishes this specific firmware's adaptive thermal availability/write capability and original configuration. It does not establish arbitrary PWM control.

MHAT's `0x40000` flag sets SCRM and requests regulated HFSP=7, except that it preserves exact full-speed HFSP=0x40. MHGT exposes SCRM in `0x10000000`, ETAU in `0x04000000`, and the performance increment in `0x02000000`; these map to restoration command flags. This supplies an OEM ownership hypothesis absent from earlier EC-only steps. Wake paths may force HFSP=7 when SCRM is set, so resume must be considered before any production owner is accepted.

One bounded native experiment captured the original configuration/flags, required Auto and the exact BIOS, set MHAT(`0x40011`) once, then observed for 30 seconds. SCRM remained confirmed by the OEM getter, generally HFSP=7 with one inconsistent EC `0x04`; service/direct RPM stayed roughly 4400–4800, not full speed. Finally MHAT(`0x11`) restored original flags/indices; immediate and ten-second Auto reads were `0x80`, final direct RPM 4500. No manual level/selector/PWM/RPM setter was called. The user initially reported consistent sound, then clarified the reply came after the test and might describe restored Auto; that regulated state's acoustic result remains unconfirmed.

A follow-up diagnostic set the previously allowlisted level 6 once with SCRM active. Thirteen observations over a minute retained state 6 and OEM ownership, RPM settled roughly 4000–4256, and native configuration plus Auto were restored. The user heard mild waving/pulsing. This still fails the requested smooth-control acceptance; the missing ownership flag is not sufficient to cure the physical complaint. Levels remain disabled in production, and the full-speed/regulated RPM gap cannot be packaged as continuous percentages.

Candidate Auto recovery now separates an explicitly unsupported Other Mode feature from a failed probe. Only known absence, no owned OEM override, and an already validated EC provider allow the existing explicit Auto recovery operation. Missing direct profile control stays disabled; IPC advertises Auto recovery separately, and Fans exposes that action independently. Transient probe failures do not opt into this fallback, and service disposal does not invoke the wider explicit recovery operation.

The in-process candidate service probe invoked the actual `ReturnFanToAuto` handler after an isolated full-speed command, without replacing the installed service or starting its IPC server/background loop. The handler returned success; independent immediate and ten-second reads both confirmed `0x80`, with RPM declining from roughly 9400 to 5644. Final cleanup also restored Auto. Assembly path/hash, response and observations are recorded in `candidate-auto-recovery-physical-test.json`. This accepts the tested candidate handler's explicit recovery operation, not the complete installed fan lifecycle or lower-speed profiles. The Fans UI now records the last explicit recovery result separately from routine telemetry, so polling cannot erase success or failure feedback; the recovery action is hidden when the service reports Auto or the explicit recovery succeeds, and a later non-Auto observation restores it.

## Native PWM getter contract checked

The installed IBM driver dispatches `0x22259C` to zero-argument PWMC and `0x2225A0` to PWMG through its inspected ACPI getter adapter at RVA `25A4`. Six read-only calls returned valid four-byte replies: capability zero and getter `0x1800`. Driver routes for PWMR/PWMS also exist, but the current HKEY namespace does not implement those methods; the similarly named SystemMemory region elsewhere is not a setter. No such setter was called.

A bounded correlation experiment sent only the previously verified full-speed command and Auto restoration. The first active legacy EC observation returned `0x04`, triggering immediate abort without reissuing. Independent immediate and ten-second restoration reads confirmed `0x80`. PWMC stayed zero and PWMG stayed `0x1800` throughout baseline, brief active observation and restored samples. Because the active interval ended early, this does not prove the getter cannot track a settled transition, and it does not establish duty, RPM or two channels. Evidence: `native-pwm-read.json` and `native-pwm-correlation.json`. The failed probe was stopped after recorded restoration; no delayed writer remains.

## LITS rejected-client acknowledgment bug

Static LITSSvc tracing shows its pipe worker calls RVA `43A50` before reading a command. This retrieves the client's process path and invokes `ValidateAssembly` from a locally hash-checked `Lenovo.AssemblyValidation.Native.dll`. Rejection disconnects the pipe without an Int32 reply. Thus the prior assumption that EOF implied accepted command was false. Candidate transport now returns failure on no reply, without retrying rejected execution as if it were a transient read. Existing critical source coverage requires this fail-closed behavior. No client-validation bypass or OEM executable impersonation is attempted.

## Lower-speed reference comparison and standard ACPI route, October 6

The [current TPFanCtrl2 implementation](https://github.com/mews-se/TPFanCtrl2/blob/444693244c5f4ac60afd83ab0bdb97a2f5a6449b/fancontrol/fanstuff.cpp) was inspected as source only. It uses the same fixed-state `0x2F` family and writes the `0x31` selector while reading and setting both fans. It supplies no verified continuous-PWM interface for this X9. Its selector writes are not copied: the inspected X9 tables reserve that selector bit. A separate [X9 owner report](https://www.reddit.com/r/thinkpad/comments/1up27hy/tpfancontrol_2_with_x9_21q6001dge/) describes pulsing in TPFanControl manual/smart modes; this is corroborating user feedback, not a proved cause or hardware contract.

The [NBFC Linux configuration tree](https://github.com/nbfc-linux/nbfc-linux/tree/59b4b4ffacf125cc79c8c7740ff2f2f8ff1343f7) contains 42 Lenovo configurations and no X9-named configuration. This is not proof that no future provider is possible. [G-Helper](https://github.com/seerge/g-helper) targets ASUS interfaces; [FanControl](https://github.com/Rem0o/FanControl.Releases) relies on available hardware backends/plugins. Neither reference establishes an X9 write contract. No third-party fan executable or driver was installed.

A fresh six-call read-only IBM-driver query again returned PWMC=0 and PWMG=`0x1800`, with valid four-byte replies. The standard Windows enumeration found `ACPI\\PNP0C0B\\0`, but no `Win32_Fan` instances. Offline review of all published ACPI tables found no `_FIF`, `_FPS` or `_FSL`. `FAN0.SRPM` only updates the cached `CRPM` variable; its `_DSM` sets notification bounds, not fan output. Thus the enumerated ACPI fan is not evidence of a working Windows percentage/RPM setter. Evidence remains private in `native-pwm-read-20261006.json`, `standard-acpi-fan-read.json` and `fan-reference-heads.json`.

The next bounded hypothesis isolates ThinkControl polling: pause only its already-installed service, issue the previously inspected SCRM/state-6 operation once, collect independent CPU temperatures and real shared tachometer readings, then restore original OEM flags, Auto and the running service. There are no selector, PWM, target-RPM or newly guessed writes. The launcher has an acceptance deadline so a late Windows confirmation cannot start a delayed test.

Result at 07:24–07:25 local: 16 active samples retained exact state 6 and SCRM, with ThinkControlService stopped throughout. Shared tachometer readings were 3244–4256 RPM (including initial ramp); independent CPU temperatures stayed at or below 56°C. The owner still heard mild pulsing. Control writes were exactly `0x06` and `0x80`; original OEM flags/indices and Auto were verified, seven-second settled Auto readback remained `0x80` at 4500 RPM, and the original service was restored to Running. No error or delayed probe remains. Evidence: `lower-polling-isolation-test.json`. This makes ThinkControl polling less likely as the sole cause; it does not prove a specific firmware defect or accept smooth lower-speed/percentage control.
